## 1. 开场：什么是异常 Exception [00:00]

这一周的主题是异常（exception）。讲师开门见山：在 Python 以及其它编程语言里，**异常指的是你代码里出的问题**。

他特意强调了一个容易误解的点：当程序里发生了"exceptional（异常的）"的事情，这**并不**是什么好事，不是说你的程序很特别、很优秀，而是**有地方出错了**，而且理想情况下你应该想办法把它解决掉。

> 讲师口头强调：exception 这个词在英语日常里好像是"出众、卓越"的意思，但在编程里它是"出错了"。别会错意。

那到底会出什么问题？讲师打开 VS Code，在终端（terminal window）里敲：

```
$ code hello.py
```

`code` 是 VS Code 提供的命令，意思是用 VS Code 打开（没有就新建）这个文件。执行后编辑器里就多了一个 `hello.py` 的标签页。

> 关于 `$` 提示符：笔记里终端命令前写的 `$` 只是表示"这是命令行里输入的命令"，你**不需要**把 `$` 也敲进去，它只是提示符（prompt）。

## 2. 第一类错误：语法错误 SyntaxError —— hello.py 现场翻车 [00:01]

讲师写了一个最简单的程序，但**故意写错**：

```python
print("hello, world)
```

注意看：字符串开头的引号有了，结尾的引号**忘了写**。讲师说这是一个你以前可能已经犯过、未来也一定会再犯的错误，而且它很隐蔽（subtle）——因为少一个字符这种事，肉眼真的不一定看得出来。

然后他"乐观地"回到终端运行：

```
$ python hello.py
```

结果屏幕上冒出来一堆红色的错误，比他写的代码行数还多。讲师自嘲：我只写了一行代码，怎么错误信息比代码还长。

但真正要读的是**最底下那一行**：

```
SyntaxError: unterminated string literal (detected at line 1)
```

**语法错误（syntax error）** 的意思是：你**打字打出来的代码本身**有问题。就像英语和其它人类语言有自己的语法，代码也有语法。这里的语法没写对，某个地方出岔子（something is awry）了，我没有正确地遵守规则。

Python 还给了一句补充说明：`unterminated string literal`。这句话很晦涩（arcane）、很让人困惑，讲师逐词拆开讲：

- **unterminated**：没结束的。我开始了某样东西，但没有把它收尾（terminate）。
- **string**：字符串，就是一串文本，Python 里叫 `str`。
- **literal**：字面量，指的是你**照字面直接敲进去的东西**。它不是一个变量，而是像 `"hello, world"` 这样你亲手打出来的文本。

所以 `unterminated string literal` = "你打了一个字符串但没把它关起来"。

**修复方法**当然是回去把引号补上：

```python
print("hello, world")
```

再运行 `python hello.py`，这回终于成功向世界问好了。

讲师在这里给了一个重要的定性：**语法错误完全是你自己的责任，必须回去从源头修改代码**。你不能指望它自己变好，也不能指望程序的其它部分帮你"接住"它。语法错误就是必须被修掉的，没有第二条路。

## 3. 第二类错误：运行时错误 Runtime Error —— 为什么要防御性编程 [00:02]

除了语法错误，Python 里还有一大类错误叫**运行时错误（runtime error）**——它们发生在**程序运行的过程中**。

这类错误的特点是：你必须**自己额外写一些防御性的代码**去检测它们什么时候发生。为什么？因为**你不知道用户会往你的程序里输入什么**。用户可能是别人，可能不认真看提示，甚至可能是恶意的、专门想把你的程序搞崩。所以你要做好准备，防御性地（defensively）去接纳用户敲进去的、甚至敲错的东西。

> 讲师口头强调（本讲核心态度）：**编程时要防御性编程（programming defensively）**。假设用户不会认真看提示，或者更糟——假设他们是恶意的、专门想让你的程序崩溃。我们要尽可能多地处理能想到的错误。

## 4. number.py 第一版：看起来对，其实有洞 [00:03]

讲师关掉 `hello.py`，新建一个文件：

```
$ code number.py
```

目标是写一个简单的程序：让用户输一个整数 `x`，然后把 `x` 打印出来。先看第一版：

```python
x = int(input("What's x? "))
print(f"x is {x}")
```

讲师一边写一边讲思路：

- `input("What's x? ")` 会在屏幕上显示提示语，等用户敲东西，然后**返回**一个字符串（`str`，string）。提示语末尾特意加了一个空格 `"What's x? "`，这样光标会往右挪一点，用户输入时好看些。
- 但我想要的是整数，不是"长得像整数的字符串"。所以要**主动**做一件事：用 `int()` 函数把这个输入转换一下。于是把 `input(...)` 的返回值当作参数（argument）传给 `int`，即 `int(input(...))`，这样最终存进 `x` 的就是一个真正的整数（`int`）。
- 打印时用 f-string（格式字符串）：`print(f"x is {x}")`。注意 `f` 前缀和花括号 `{x}`——只有加了 `f`，Python 才会做插值（interpolate），也就是把变量 `x` 真正的**值**塞到花括号的位置上。不加 `f` 的话，屏幕上就会字面印出 `x is {x}`。

运行一下，输入 50：

```
$ python number.py
What's x? 50
x is 50
```

看起来一切正常。

**然后是本讲的第一个灵魂拷问**：讲师问，"或者，它真的对吗？"——什么都没出错，但这个程序里**仍然可能**出什么问题？特别是，如果不是我本人、而是另一个人在用它的时候？

他点了观众回答。第一位同学的回答（有点听不清），讲师复述并确认：**如果用户输的根本不是整数，你就不能盲目地把它转成 `int`**。

## 5. 边界测试：0、负数、cat → ValueError [00:04]

讲师说，我们来**模拟**这个问题。测试代码时，一个好习惯是测**边界情况（corner case）**——不要只测 49、51 这种"最普通"的数字，要挑点数学上更有意思的：

```
$ python number.py
What's x? 0
x is 0
```

`0` 是边界情况，没问题。再试负数：

```
$ python number.py
What's x? -1
x is -1
```

负数也 OK。正数、负数、0 都试过了。现在试最后一个：一个 **cat**（猫）——也就是敲一个完全不像数字的字符串：

```
$ python number.py
What's x? cat
```

回车之后，出现了**另一种**错误：

```
ValueError: invalid literal for int() with base 10: 'cat'
```

讲师强调这不是语法错误——他没有打错字，没有漏掉某个语法成分。这是**某个值（value）**出了问题，而且这个值是他写这段代码时根本没预料到的：是"人"（此时就是他自己）在代码写完很久之后敲进去的。

## 6. 怎么读懂 Python 的错误信息 [00:04]

这个报错叫 **ValueError**，说明信息是：

```
invalid literal for int() with base 10: 'cat'
```

讲师坦率地说：这句话也挺拗口（a bit of a mouthful）的。不幸的是，Python 以及很多编程语言，**错误信息是写给已经很熟练的程序员看的**。而你第一次学编程时，连语言本身都不熟，更别提这些报错了。所以要学会**拆解**：

- **invalid literal**：无效的"字面量"。literal 还是那个意思——直接敲进去的东西。
- **for int()**：对 `int` 函数来说。
- **base 10**：十进制。这是 Python 的默认进制，就是我们日常用的 0-9 那套数字系统。
- **'cat'**：最后 Python 真正嫌弃的东西——我把 `"cat"` 传给了 `int()` 函数。

一句话翻译：**你给 `int()` 传了个 "cat"，它不是十进制数字，转不了**。

那怎么修？

讲师先给了一个"看起来能行其实没用"的方案：在程序里多加一行 `print`，明确告诉用户"请输入整数"或者"别输 cat、别输字符串"。

但立刻自我否定：**用户可能根本不看你的提示**。这招不是有效的策略。

真正要做的是——**带着"错误处理（error handling）"的意识去写代码**。我们写的代码不仅要完成我们关心的事，还要能处理那些可能意外发生的错误。

> 讲师口头强调：错误处理不是补丁，是设计的一部分。

## 7. try 与 except：第一次修好 [00:05]

在 Python 里怎么做到？答案是一个关键字：**`try`（尝试）**。名字很贴切——如果你想"试着"做某件事，就可以用这个关键字，然后检查是不是发生了异常的、出错的事情。

跟 `try` 配对的另一个关键字是 **`except`（除了）**：试着做某事，**除非**出错了，那就做点别的。

于是第一版改进代码：

```python
try:
    x = int(input("What's x? "))
    print(f"x is {x}")
except ValueError:
    print("x is not an integer")
```

讲师边写边强调三个细节：

1. 在原来代码上面写 `try` 加冒号 `:`，告诉 Python"试着做下面这些"。
2. 把原来的两行代码**缩进（indent）**相同的空格数（这里是 4 个空格）。
3. 新增的一行写 `except ValueError:`。**注意大小写**：`V` 和 `E` 都必须大写。这些符号是**大小写敏感（case sensitive）**的，写成 `valueerror` 就不对了。

冒号后面（缩进起来）就是"出异常时我想做的事"。这里简单打印一句 `x is not an integer`，至少告诉用户问题大概是什么。

**缩进很重要**：`try` 在第 1 行，第 2、3 行缩进了，所以这两行就是"被尝试"的代码；第 5 行（缩进在 `except` 下面）才是出错时执行的代码。

运行测试：

```
$ python number.py
What's x? 50
x is 50
```

输入 50 正常。再输入 cat：

```
$ python number.py
What's x? cat
x is not an integer
```

现在干净多了。用户不会看到那个吓人的、他根本不知道该怎么办的默认 Python 报错。**是程序员你**提前预判了"可能会有异常发生"，并且替用户把这个错误处理掉了，给出了一句恰当的提示。

## 8. 学生提问：只有 ValueError 一种吗？[00:08]

**学生**：value error 是唯一能捕获的错误类型吗？还有别的吗？

**讲师**：还有别的错误，今天我们会再看到几种。说实话，如果你继续写 Python，接下来几周、几个月、几年里你会见到**非常多**种错误。但**处理它们的手法大体上是相同的**。

> 这段话很关键：不要去背错误类型，要掌握 `try/except` 这一套通用手法。

## 9. 学生提问：能不能不写错误类型、全都接住？[00:09]

**学生**：要用 `except` 块，你得先知道错误的类型对吧？那如果**我没法预料**具体是哪种错误怎么办？

**讲师**：非常好的问题。我现在这么做是很"乖"的——我确切知道 `int()` 函数在什么情况下会抛出什么类型的错误（`ValueError`）。我不知道它什么时候发生（那取决于用户），但我知道**类型**。

Python 确实提供了一种写法：直接写 `except:`，不写错误类型，意思是"不管出什么错都接住"。

**但讲师明确反对**，给了两条理由：

1. **它会隐藏你代码里的其它 bug**。如果你不知道到底出了什么错，你怎么可能正确地处理它？
2. 换个说法就是——**这是偷懒（lazy）**。写一句"全都接住，我在这儿统一处理"，是懒惰的写法。

更好的做法是：**弄清楚可能会发生哪些错误，然后像我这样显式地写出来**。

不过讲师也很诚实地补了一句"自相矛盾"的现实：等你以后去读 Python 官方文档时，会发现文档**并不总是主动告诉你**某个函数会抛出哪些错误。所以这个建议有点自我矛盾——"你应该这么做，但又不总清楚该检查什么"。怎么办？**靠练习，你会越来越熟**。而且有时候文档确实会写清楚。

## 10. 最佳实践：try 里只放最少的那几行 [00:11]

回到代码。讲师说这版比之前好、更正确了——至少用户不会看到那个丑陋的、绝大多数人不知道怎么办的默认报错，我处理得更优雅，还打印了 `x is not an integer`，更有指导性。

**但这还不是最好的实现。为什么？**

"因为我在这里其实还是有点懒。"注意看，我在 `try` 里面放了**两行**代码。虽然只有两行，不是什么大事，**但既然要讲最佳实践（best practices），那就该讲透：你应该只把"真的可能抛异常、真的可能失败"的那一两行放进 `try`。**

而 `print(f"x is {x}")` 这一行，讲师说他**相当确定**不会抛出 `ValueError`——不管 `x` 是 `int`、`str`、`float` 还是别的什么，Python 的 f-string 都能把它好好打印出来。

所以把第 3 行移到底部，不再缩进：

```python
try:
    x = int(input("What's x? "))
except ValueError:
    print("x is not an integer")

print(f"x is {x}")
```

## 11. 新坑：NameError: name 'x' is not defined [00:14]

讲师说：我做了件好事（只 `try` 最少的必要代码），**但我担心我引入了一个新错误**。来看看现在哪里不对了。

```
$ python number.py
What's x? 50
x is 50
```

输入 50 一切正常。**但别忘了测边界情况**——0、负数，还有这次的 cat：

```
$ python number.py
What's x? cat
x is not an integer
Traceback (most recent call last):
  File "number.py", line 6, in <module>
    print(f"x is {x}")
NameError: name 'x' is not defined
```

**好家伙，又是一种新错误：`NameError`（名字错误）。**

- `ValueError` 指的是**值**有问题——某个变量的值、某个人输入的值不对。
- `NameError` 通常指的是**你的代码**有问题——你在对某个变量的**名字（name）**做不该做的事。

错误信息说 `name 'x' is not defined`，并且**明确指出了 line 6（第 6 行）**，所以我知道问题出在第 6 行。

## 12. 学生抢答：是作用域 / 局部变量的问题吗？→ 都不是 [00:15]

讲师问大家：为什么 `x` 在第 6 行不存在？我明明在第 2 行定义了它啊？

**学生 A**：也许是变量的作用域（scope）只在 [听不清] 里面？

**讲师**：术语用得很好。**作用域（scope）指的是变量存在的那段代码范围**。但这个答案**在 Python 里不对**。在 C、C++、Java 里，缩进或花括号确实会定义变量的作用域，那个思路在那儿成立；但这里不成立——而且注意，**刚才这代码还是能跑的**，我前面明明成功打印出了 `x is 50`。所以 `x` 在第 2 行定义之后是存在的。

再来一个假设？

**学生 B**：是不是因为它是局部变量（local variable），出了作用域就没定义？因为 input 是在 `try` 里面提示的，外面就没定义了。

**讲师**：直觉很好，术语也很好。确实有**局部变量**（通常存在于函数内部）和**全局变量**（通常存在于整个文件）的概念。但在这个例子里，**仍然不是这个原因**。

## 13. 真正的原因：赋值是从右往左，右边先炸了 [00:16]

那到底是什么？答案归结为四个字：**执行顺序（order of operations）**。

回到第 2 行 `x = int(input("What's x? "))`，回忆一下讲赋值运算符（单个等号 `=`）时说的：**它把右边的值复制到左边**。那么想一想，出错是在哪一步？

- `input()` 函数大概没毛病——我们已经用过很多次了，它总是返回一个字符串（`str`）。
- 那问题在哪？**在我把这个字符串作为参数传给 `int()` 的时候，是 `int()` 函数出错了。**

回想更早那次 `ValueError`：确实是 `int()` 函数不喜欢 `"cat"` 这个输入。

所以，**等号右边**的那部分代码才是制造问题的地方，才是产生 `ValueError` 的地方。

关键点来了：

> **因为 `ValueError` 发生在等号右边，所以没有任何值被复制到左边。错误打断了整个过程。**

也就是说，虽然你看到第 2 行写着 `x = ...`，但**等号左边的部分最终根本没被执行到**——因为 `ValueError` 发生得太早了。

于是当程序好不容易走到第 6 行时：我**看起来**在第 2 行定义了 `x`，如果一切顺利我**本该**在第 2 行定义它，但**我们根本没走到"从右往左复制值"那一步，错误先发生了**。所以这代码现在是错的。

> 这是本讲**最精华的一段推理**，值得反复读：出错发生在赋值语句右侧 → 赋值没完成 → 变量从来没被创建 → 后面用到它的地方就 `NameError`。

## 14. else：try 成功时才执行 [00:18]

怎么解决？Python 的 `try` 语法还支持另一个关键字：**`else`**。

我们之前见过 `else`——讲条件语句时有 `if`、`elif`、`else`，`else` 是那个"兜底"的分支：其它情况都不适用时就走它。

这里**直觉是一样的**：试着做下面的事（`try`），如果出错了就这样（`except`），**但如果没有出错，就那样（`else`）**。

```python
try:
    x = int(input("What's x? "))
except ValueError:
    print("x is not an integer")
else:
    print(f"x is {x}")
```

现在的逻辑是：

- 无论如何，Python 都会先试着执行第 2 行。
- 如果出错了，执行 `except` 里的代码处理 `ValueError`。
- **但如果 `try` 成功了，就没有异常要处理，于是执行 `else` 里的代码。**

讲师承认这可能有点让人困惑：`else` 既用在条件语句（`if/elif/else`）里，又用在 `try/except` 里。但这没关系，这就是语言的一部分、是它的特性之一。

实测：

```
$ python number.py
What's x? 50
x is 50
```

输入 50 时：第 1 行执行（"我要试着做下面的事"）→ 第 2 行执行，转换成功，50 从右复制到左存进 `x` → **没有异常发生**，所以跳过 `except` → 直接跳到 `else` 里的 `print`，打印结果。

再测 cat：

```
$ python number.py
What's x? cat
x is not an integer
```

这回我们看不到 `x is` 什么，只能看到 `x is not an integer` —— 这是 `except` 子句（clause）里处理的内容。

## 15. 学生提问：能再讲一遍 NameError 吗 [00:21]

**学生**：能重复讲一下这个……try 函数吗？

**讲师**：重复讲 Name Error？是这个 name error 有什么问题吗？（学生：对，对。）

**讲师**：好，我们把时间倒回去一点点，回到**我还没用 `else` 修好它之前**的那个版本。当时代码是这样的，运行 `python number.py`、输入 cat，得到 `name 'x' is not defined`，Python 说问题在第 6 行。

2. 那 `x` 应该在哪儿被定义？大概是在第 2 行。
3. 那会出什么问题？如果用户输入了不像数字的东西，比如 cat，那么把 `input()` 的返回值（"cat"）传给 `int()` 去转整数，**毫无意义**——你根本不可能把 C-A-T 转成整数。

## 16. 还不够友好：用 while True 循环反复追问 [00:23]

讲师继续提要求：现在代码对了，但对用户**不太友好**——用户没给整数，我就把他拒了、直接**退出程序**，这样合适吗？

更友好的做法是：**重新提示（reprompt）**用户，一次又一次地问，直到他配合、给了你想要的东西（一个数字）。

那用什么 Python 特性可以"一次又一次"地做某件事？**循环（loop）**。学生齐答 loop。

于是把整个 `try/except` 缩进到一个循环里面：

```python
while True:
    try:
        x = int(input("What's x? "))
    except ValueError:
        print("x is not an integer")
    else:
        break

print(f"x is {x}")
```

讲师解释 `while True`：

- `while` 关键字会引发一个循环，它会问一个问题——一个布尔表达式（Boolean expression），结果必须是 `True`（真）或 `False`（假）。
- 如果我想让它**永远循环**（至少一开始是），那就直接写 `while True`，因为"真就是真"。
- 效果就是：**无论如何都会一直做某件事，除非我们提前 `break` 出去**。

现在的流程：试着拿一个 `x`；如果有 `ValueError` 就打印 `x is not an integer`；**如果用户这次成功给了数字，就 `break` 出循环**；出循环后执行最后的 `print`。

实测：

```
$ python number.py
What's x? 50
x is 50
```

控制流（control flow，也就是程序逻辑的走向）是这样的：

1. 我在第 1 行，身处一个循环里（希望能出去）。
2. 第 2、3 行：尝试获取用户输入并转成 `int`。
3. 这次我"很配合"地输入了 50，它长得像数字、也确实是数字，`int()` 转换成功，50 从右复制到左存进 `x`。
4. `except ValueError`？——**没有** ValueError，因为我输入的是数字，没发生任何异常。这是一次"无聊的、正常的"执行。
5. 于是 **`break` 出循环**（注意 `else` 是跟着 `try` 的，不是跟着 `except` 的）。
6. 出了循环，打印 `x`。

再测不配合的情况：

```
$ python number.py
What's x? cat
x is not an integer
What's x? dog
x is not an integer
What's x? bird
x is not an integer
What's x? 50
x is 50
```

**这是一个新特性（行为）了**：我被明确告知做错了什么（`x is not an integer`），拿到了有用的反馈，而且**又被提示了一次** `What's x?`。可以一直这样下去——只要我处在无限循环里，就会一直问，直到我"试着成功了"才 `break` 出去。

## 18. 学生提问：break 只能放 else 里吗？[00:27]

**学生**：`break` 可以用在 `except` 和 `else` 里面吗？比如在 `else` 里打印，能不能把 print 和 break 一起用？

**讲师**：可以在循环里用 `break` 跳出循环；也可以在条件语句（`if` / `elif` / `else`）里用；也可以在 `try` / `except` / `else` 语句里用。**任何时候你在一个想跳出的循环里，都可以用 `break` 这个关键字**。

我在这里是在"异常"的语境下用它，但它**并不局限于**这个场景。

而且讲师还演示了另一种写法：**`break` 甚至不必放在 `else` 里**。可以去掉 `else`，把 `break` 直接放在 `try` 里：

```python
while True:
    try:
        x = int(input("What's x? "))
        break
    except ValueError:
        print("x is not an integer")

print(f"x is {x}")
```

为什么这样逻辑上也成立？

- 我要试着执行第 3 行：把用户输入转成 `int`，并从右往左存进 `x`。
- 如果出错了，代码会**立刻跳转**到 `except` 去处理异常。
- **如果没出错，我的代码自然就一行一行继续往下执行**，所以理论上把 `break` 放在这里是说得通的。

运行 `python number.py`，输入 50，成功跳出循环。

**那么哪种更好？** 讲师的诚实回答：**真不好说，两种都说得过去**。

- 这个程序很短，虽然我现在 `try` 里放了两件事，但其中 `break` 那件事是不可能失败的——你要么 break，要么不 break，没有任何用户数据会影响它。所以严格来说我们**不需要**把这两行都放那儿。
- 但它只有两行，所以我觉得也还行。
- 回忆一下我们以前讨论过的：**不只是"正确性"（correctness，代码是否按预期工作），还有"设计"（design）**。两种写法都有道理：
  - 如果你更喜欢这种写法**可读性好、没有 `else`**，那没问题；
  - 如果你更喜欢**尽量减少 `try` 里的行数**（以防出错），那用 `else` 也是合理的方案。

> 这里其实是本讲的一个"设计观"启蒙：代码没有唯一正确答案，但你要**有意识地做选择**，并且能说出理由。

## 19. 封装成 get_int() 函数 + main() [00:30]

继续改进。讲师设想：假设我今天、明天都要经常从用户那里拿数字。那就像以前学过的那样，**自己发明一个函数 `get_int`** 来"从用户那里拿一个整数"，今天用、明天用，甚至还能分享给别人用——如果他们也想写从用户那里取整数的程序。

怎么做？删掉 `print`，保留大部分循环，然后定义函数、把已有代码全部缩进到函数体里：

```python
def main():
    x = get_int()
    print(f"x is {x}")

def get_int():
    while True:
        try:
            x = int(input("What's x? "))
        except ValueError:
            print("x is not an integer")
        else:
            break
    return x

main()
```

要点：

- 现在有了一个 `get_int` 函数（暂时不接受任何参数），它试着从用户那拿一个 `int`；出 `ValueError` 就"吼"一句 `x is not an integer`；否则 `break`。
- **但既然现在是函数了，光 `break` 不够**。回忆一下"返回值（return value）"那节课：如果你发明的函数其存在的意义不只是"打印点东西"这种副作用（side effect），而是要**交回一个值**（就像以前那张便利贴的比喻），那么你必须**显式地 `return x`**。
- 一旦我们开始自己造函数，通常也顺便定义自己的 **`main` 函数**——程序的主干部分。
- 文件的最底部调用 `main()`，这样无论如何，**所有东西都定义完之后**才会去执行主函数。

运行测试（50 成功；cat、dog、bird 都被拒并重新提示；最后 50 成功打印）都和之前一样。

讲师指出这版代码的**好处**：

1. 我把"获取一个整数"这件事**抽象（abstract away）掉了**。
2. 整个程序现在本质上就只剩 `main` 里那三行代码（`x = get_int()` 和 `print`）。为什么？因为我把"从用户那拿整数"的整套流程抽象进了我自己发明的 `get_int` 函数里。

## 20. 精简一：else 里直接 return x [00:33]

还能改进吗？我保证这版是**正确的**：它处理了错误，也返回了 `x`。但严格来说**不需要写这么长**。

注意看：如果 `else` 里做的事只是 `break`，而紧接着（按缩进）下一步就是 `return x`——**那你为什么要浪费大家的时间？** 一旦你知道自己已经准备好要返回值了，直接 `return x` 就行了。

```python
def main():
    x = get_int()
    print(f"x is {x}")

def get_int():
    while True:
        try:
            x = int(input("What's x? "))
        except ValueError:
            print("x is not an integer")
        else:
            return x

main()
```

讲师解释 `return` 与 `break` 的关系：

- `return` 用来**从函数返回值**，`break` 用来**跳出循环**。
- 但 **`return` 比 `break` 更强（stronger）**：它不仅能把你带出循环，还能顺便返回一个值。也就是说，**它一个动作干了两件事**。

## 21. 精简二：学生提议 —— try 里直接 return [00:34]

还能更紧凑吗？如果目标只是"把代码收紧"（尽管它已经正确了），还能怎么改？**减少行数 = 降低出错概率 + 更好读**。

**学生**：你可以直接在 try 那里返回值啊，拿到 input 的 x 然后 return x。

**讲师**：对，我们可以把 `return x` 往上提一点。（顺便纠正一下大家的用词：**这不是 try "函数（function）"，准确说是 try 语句（statement）**。）

我其实**并不需要 `else`**。如果真想，我可以在第 9 行后面直接 `return x`。

而且——回忆一下以前讨论过的"不要定义不必要的变量"：如果我在这里定义了变量，马上在下一行用一次，之后就再也不用了，**那为什么要定义它？** 于是可以省掉这一行，甚至**根本不显式定义 `x`**：

```python
def main():
    x = get_int()
    print(f"x is {x}")

def get_int():
    while True:
        try:
            return int(input("What's x? "))
        except ValueError:
            print("x is not an integer")

main()
```

也就是直接 `return int(input("What's x? "))`，一次性把"拿输入 → 转整数 → 返回"三步做完。

**哪种更好？** 讲师说：我不知道，理智的人可能会有不同意见。

- **一方面**：代码收紧了，行数更少，更好读，我写错的概率更低。
- **另一方面**：**理解起来稍微复杂了一点**，而且"我从哪儿返回的"这件事**没那么一目了然**。

两种说法都站得住。讲师给出最后的判断标准：

> **最重要的是：你是有意识地做出这个选择的。** 你决定用这种写法或那种写法，并且**你能在心里给出理由**——而不是说"呃，它能跑，我就不管了"。**要有个好理由**，而好理由会随着经验和练习而来。

## 22. 术语纠正：try 是语句 statement，不是函数 function [00:35]

（承接上一段）学生说 "the try function"，讲师当场纠正：

> **这不是 try 函数（function），技术上说它是 try 语句（statement）。** 函数（function）通常带括号（一对括号）。`try` 这里没有括号，它只是一个语句（statement）。

这个区分在后面读文档、看报错时会一直有用：`if`、`while`、`for`、`try` 都是**语句**；`int()`、`input()`、`print()` 才是**函数**。

## 23. pass：抓到异常但什么都不做 [00:36]

最后一个"体验"层面的改进：你可能觉得程序有点吵——一直对用户说 `x is not an integer`、`x is not an integer`、`x is not an integer`，挺烦的（obnoxious）。

如果你想**温和一点**，只用同样的提示语再问一遍：`What's x?`、`What's x?`、`What's x?`，一次又一次，可以吗？可以。

这里引入关键字 **`pass`**。

讲师的比喻非常形象：如果你想在 Python 里**处理一个异常，但又想"跳过"对它做任何事**——也就是你**想接住它，但本质上想忽略它**。你不想打印任何东西，也不想退出程序，你只想**静默地忽略**它。

就像你在一个满屋子人的房间里，轮到你发言了，你却说：**"pass（过）"**。他们还是在叫你，但你不再多说、也不再多做任何事。

于是把 `print("x is not an integer")` 换成 `pass`：

```python
def main():
    x = get_int()
    print(f"x is {x}")

def get_int():
    while True:
        try:
            return int(input("What's x? "))
        except ValueError:
            pass

main()
```

讲师强调 `pass` 的语义：

- 我**仍然在捕获（catch）这个异常**，所以用户不会看到任何提到 `ValueError` 的可怕信息——**我的代码接住了它**。
- 但我**什么都不说（pass on saying anything about it）**。
- 我会**留在循环里**，继续提示、再提示用户。

效果：

```
$ python number.py
What's x? cat
What's x? dog
What's x? bird
What's x? 50
x is 50
```

**哪种更好？** 讲师又一次给出两面看法：这样可能更友好一点——你只是在温和地提醒用户你想要什么。但**也可能更糟**——因为用户可能**不知道你为什么**一遍又一遍地问他。这事儿不明显，所以两种做法都说得过去。

关键是：**这只是又一种处理错误的机制**。我们用 `except` 捕获**特定**的错误，但**不必**对它做更多处理，可以 `pass` 掉。

## 24. 学生提问：缩进到底是什么意思（超详细解释）[00:38]

**学生**：关于你发明 `get_int` 函数这件事……我一直在琢磨整个逻辑，比如 `while True: 做这个`。我想请你**再详细讲讲代码的缩进（indentation）**。

**讲师**：这个缩进是**刻意的、有逻辑含义的**。有些语言不要求这么严格的缩进，你可以用花括号或者别的符号来表明"什么属于什么"。

**通用规则**：在 Python 里，**只要你写了一行代码，而它下面的行被缩进了，那就意味着那些行在某种程度上"属于"上面那一行**。而且可以推断：**这些缩进的行，只有在第一行指示计算机这么做的时候，才应该被执行。**

然后讲师拿当前代码逐行数了缩进（以 `pass` 版为准）：

```python
1  def main():
2      x = get_int()
3      print(f"x is {x}")
4
5
6  def get_int():
7      while True:
8          try:
9              return int(input("What's x? "))
10         except ValueError:
11             pass
12
13
14 main()
```

逐条解读（**数空格数**）：

- **第 6 行**：`def get_int():`，定义了一个叫 `get_int` 的函数，不接受参数，冒号结尾。**此后所有缩进至少 4 个空格的行，都属于这个函数**。为什么？**这就是 Python 语言的设计**。
- 讲师补了一句：坦白说，我觉得设计者是**看烦了 C、C++、Java 里那些不强制缩进的丑陋代码**，所以把缩进**内建进语言里**了。（他还自嘲说自己的"编年史"可能不太准，但确实有很多语言在缩进这件事上比 Python 松散得多。）
- **第 7 行**的缩进同样有意义：`while True:` 缩进了 4 个空格，说明**它是 `get_int` 函数的一部分**。
- 而 `while True` 下面，有 8 个空格的、有 12 个空格的、有 8 个的、有 12 个的——讲师说他就是在快速数那些"点"。**这意味着它下面这些行都在那个 `while` 循环里面**。`while True` 的意思是：**反复执行第 8 到第 11 行**（可能会有选择地执行），一遍又一遍。
- **第 8 行**：`try` 下面缩进了第 9 行，意思就是"你要尝试的就是第 9 行这件事"。
- **第 10 行**：`except ValueError:` 下面缩进了第 11 行，意思是"**只有**在出现 `ValueError` 异常时，才 `pass`"。

讲师总结：**缩进只表示"什么属于什么"。** 一旦你习惯了，你会发现**光靠缩进就能解释程序的逻辑**。

而且它有个**极好的副作用**：对你自己（第二天早上的你）、对你的同事、家人、朋友、老师来说，**你的代码可读性大大提升**，而不是一坨乱糟糟的文本。

> 这一段是本讲关于"Python 缩进"的最完整解释，值得单独记住：**缩进 = 归属关系**。

## 25. 学生提问：pass 之后调用者还能知道出错了吗？isnumeric 行不行 [00:40]

**学生（两个问题）**：
1. 一旦你写了 `pass`，**调用者（caller）还能不能通过某个系统变量之类的方式，得知这个错误的任何信息？**
2. Problem Set 0 里提到了一些字符串方法，包括 **`isnumeric()`**——用它（先判断再转换）和现在这种做法有什么不同吗？

**讲师（问题 1）**：好问题。**如果我用这种方式处理错误，调用者是得不到任何信息的。** 这正是"我来处理它"的**目的所在**——让 `main` 或者其它调用者**不知道**技术上曾经出过问题。

**讲师（问题 2）**：`isnumeric()` 是另一个你可以调用的函数（严格说是字符串方法），它能检查一个字符串、判断"这是不是一个数字"。

我**完全可以**用那套机制：用一个条件语句，**如果**这看起来像数字，**就**把它传给 `int()` 并转成整数。这完全没问题。

但讲师给出了他的偏好：

> 一般来说，我认为 **Pythonic（符合 Python 风格的）做法**——不管好坏——是：**先试着做，希望它能成；如果不成，就处理异常。**

其它语言更倾向于"检查、检查、检查"——一堆 `if`、`elif`、`else` 条件判断。而 **Python 的心态更多是："嗯，试试看。但确保你把错误处理好。"** 所以（用 `try/except`）**这是更 Pythonic 的做法**。

不过讲师立刻补了一句：**你的做法（先用条件判断是不是数字）也完全合理**，如果你想走那条路的话。

> 记一个词：**Pythonic** = 符合 Python 惯例 / 风格的写法。本讲提倡的就是这种"先 try、出错再处理"的 Pythonic 风格。

## 26. 最后一改：给 get_int 加 prompt 参数 [00:42]

最后一处改进。注意现在 `get_int` 里**硬编码（hard-coded）**了 `x` 这个词——也就是手动把 "What's x?" 敲死在函数里了。（hard code = 手工写死在代码里，缺乏灵活性。）

我们想让 `get_int` **更可复用（reusable）**。

现在的情况是：我在靠"君子协定（honor system）"——`main` 里定义了个变量叫 `x`，`get_int` 里也问一个叫 `x` 的变量。**但最好是：调用者（caller）不需要知道被调用者（callee）给它的变量取了什么名字，反之亦然。**

> 术语：**caller（调用方）** = 使用某个函数的函数（to call a function 就是使用它）；**callee（被调用方）** = 被使用的那个函数。

所以我不该只是"希望"两处的 `x` 恰好是同一个。改进方案：**给 `get_int` 加一个参数（parameter）**。

也就是说：如果 `main` 想用 `get_int`，那 `main` 大概应该**告诉 `get_int` 要给用户显示什么提示语**。就像 Python 自带的 `input()` 函数一样——**由你来传入一个 prompt（提示语）**，用户被问到时就会看到它。

最终版：

```python
def main():
    x = get_int("What's x? ")
    print(f"x is {x}")

def get_int(prompt):
    while True:
        try:
            return int(input(prompt))
        except ValueError:
            pass

main()
```

要点：

- `get_int` 现在接受一个参数，叫 `prompt`。讲师说"我可以给它取任何名字，但 `prompt` 在英语里相当自明（self-explanatory）"——它的意思就是**用户会看到的那条消息**。
- 到下面真正调用 `input()` 时，我**不必自作主张地**写 "What's x?"——**万一是调用它的程序想问 `y` 或 `z`、或者别的什么变量呢？** 我只要把调用方传进来的 `prompt` 交给 `input()` 就行了。
- 这样我写出了**更可复用的代码**。**功能（functionality）本身没变**，但现在它更"动态"了一点：`get_int` **不需要知道、也不关心**在问什么变量、问的是什么，它只需要知道**该给用户显示什么提示语**。

运行验证（输入 50 成功；输入 cat 会被静默忽略并重新提示；cat、dog、bird 都会用**同样的提示语**继续追问），因此这段代码**可用性更强**了。

最后讲师预告了一个新关键字：**你还可以用 Python 的 `raise` 关键字自己抛出异常（raise exceptions yourself）**，不过这个以后再说。

## 本讲易错点

1. **语法错误没法被 `try` 接住。** `SyntaxError` 必须你自己回去改代码，不存在"捕获语法错误"这回事。
2. **忘了闭合引号 / 括号** 是最典型的语法错误，报错是 `unterminated string literal`，很隐蔽，肉眼容易漏。
3. **`except ValueError` 大小写敏感。** `V` 和 `E` 必须大写，写成 `valueerror` 或 `Valueerror` 都不行。
4. **不要裸写 `except:`**（不写错误类型）。它会掩盖代码里其它真正的 bug——你连出了什么错都不知道，怎么可能处理对？这是懒惰的写法。
5. **`try` 里只放最少的代码。** 把不会出错的 `print` 之类放进 `try`，是不必要的；但也别为了极端纯粹而牺牲可读性——本讲里两种写法讲师都说可以接受。
6. **`NameError` 的常见成因之一：赋值语句右边先抛异常。** `x = int(input(...))` 里 `int()` 出错时，等号左边的赋值根本没发生，`x` 就从来没被创建，后面用 `x` 就会 `NameError`。
7. **这不是作用域问题。** 在 Python 里，`try` 的缩进**不会**创建新的变量作用域（这跟 C / C++ / Java 不同）。出错原因是执行顺序，不是作用域。
8. **`else` 是跟着 `try` 的，不是跟着 `except` 的。** 语义是"`try` 成功、没有异常时才执行"，不是"`except` 的兜底"。`else` 在这里和条件语句里的 `else` 含义不同，别混。
9. **忘了 `break` / `return` 就变成死循环。** 把 `print` 挪进循环却不 `break`，程序会永远问下去。
10. **`pass` 不是"跳过这次循环"，它是"什么都不做"。** 它仍然**捕获**了异常（用户看不到报错），只是不打印、不退出；循环会自然继续，于是表现为"重新提示"。它**不是**"跳过本次循环"的意思。
11. **`return` 比 `break` 更强**：`return` 既能跳出循环，又能返回值，一个动作干两件事。
12. **缩进在 Python 里有语义。** 下一行缩进 = 它属于上面那一行；4 空格、8 空格、12 空格分别代表"属于函数 / 属于循环 / 属于 try 或 except"。不要用空格数去数，要看层级。
13. **`try` 是语句（statement），不是函数（function）。** 函数有括号（`int()`、`print()`），`try` / `if` / `while` / `for` 都没有，它们是语句。
14. **别把提示语硬编码在函数里。** 加上 `prompt` 参数，函数才可复用——调用方（caller）不需要知道被调用方（callee）内部给变量取了什么名。
15. **Pythonic 的处理风格是"先试再说"（try it, handle the error）**，而不是用 `if isnumeric()` 之类先检查一堆条件；不过后者也完全合理，重要的是你**有意识地做出选择并能说出理由**。
