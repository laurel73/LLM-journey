## 本讲速览

**一句话主题**：不要靠手动运行程序来"肉眼验证"，而要用**代码测试代码**——先用 Python 自带的 `assert`（断言）关键字表达"我认为某件事必然成立"，再借助第三方工具 `pytest`（单元测试框架）自动批量跑测试、自动收集线索，最后把测试文件组织进 `test` 文件夹一键运行。

**本讲知识清单**

1. 为什么要自己写测试：手动跑几次输入不算测试，会漏掉边界情况（corner cases）
2. `if __name__ == "__main__":` 的真正用途：让文件可以被安全 `import` 而不自动执行 `main`
3. 测试文件的命名约定（`test_` + 被测文件名，如 `test_calculator.py`）、从别的 `.py` 文件导入函数（`from calculator import square`，把文件当模块用）、测试函数的命名约定（`test_` + 被测函数名，如 `test_square`）
4. 第一版手写测试（`if ... != ...:` + `print`）与"故意造 bug"：`n + n` 代替 `n * n` 时，只测 2 会"幸运地通过"（2+2 == 2\*2）
5. `assert` 关键字：断言一个布尔表达式为真，为假则抛出 `AssertionError`（断言错误）
6. `try` / `except AssertionError` 手写友好报错：能用，但代码量爆炸（31 行代码测 2 行函数）
7. 代表性取值的思路：正数、负数、0，覆盖不同类别而不是穷举
8. `pytest` 的安装与运行：`pip install pytest` + `pytest test_calculator.py`
9. 读懂 pytest 输出：红色 `F` 表示失败，红色 `E` 标出真正出错的那一行，`6 == 9` 这类线索
10. 拆分测试函数：`test_positive` / `test_negative` / `test_zero`，一个失败不阻断其他测试
11. 测试"应当抛异常"的场景：`with pytest.raises(TypeError): square("cat")`
12. 副作用（side effect）与返回值：`print` 没有返回值，无法用 `assert` 比较；改造 `hello.py` 为 `return f"hello, {to}"`，把 `print` 交给调用方，函数才可测试
13. 测试里可以用 `for` 循环批量断言，但测试本身要尽量简单——不要写"测试测试的代码"
14. 用文件夹组织测试：`mkdir test`、`test/test_hello.py`、空的 `__init__.py`、`pytest test`

## 0. 开场：别再靠"手动跑一遍"来测试了 [00:00]

到目前为止，我们写了不少代码。以前的测试方式大概是这样的：写一段代码，运行程序，手动输入几个样本值，看看结果对不对；然后再运行一次，再输几个值。或者——更糟——干脆等着别人（比如 CS50 的 check50）来帮你测。

但更好的做法，是尽早养成一个习惯：**用你自己的代码来测试你的代码**。不管你是在写个人小项目还是在工业界干活，现在非常普遍的做法是：不只写"解决问题"的代码，还要额外写一小段"测试这些代码"的代码。这就是这一讲的主题。

这么做的好处很直接：你会对自己解决的问题"确实被正确解决了"更有信心、更有把握。

**补充术语**：所谓 **unit test**（单元测试），是一种正式的说法，意思是"测试你程序里的一个个单元"。这些"单元"通常就是**函数**。所以单元测试基本等价于"给你自己写的函数写测试"。

## 1. 回到几周前的 calculator.py [00:01]

我们把时间倒回几周前，回到那个"计算数字"的程序。当时的进度停在"计算一个数的幂"，比如 x 的平方，x 可能是 2、3 或者别的数字。

David 在终端里重新打开这个文件：

```
$ code calculator.py
```

（`$` 是终端提示符，它后面的才是你要敲的命令。`code` 是 VS Code 的命令行命令，意思是"用编辑器打开这个文件"。）

代码恢复到当时的样子：

```python
def main():
    x = int(input("What's x? "))
    print("x squared is", square(x))


def square(n):
    return n * n


if __name__ == "__main__":
    main()
```

说明一下这里在干什么：

- `main` 函数里，先用 `input`（输入）拿到用户输入，再用 `int()` 把它转成整数，存进变量 `x`；
- 然后 `print`（打印）两个东西：`"x squared is"` 这个字符串，以及调用 `square(x)` 的结果，作为 `print` 的第二个参数传进去；
- `square` 函数接受一个参数，当时我们管它叫 `n`（number，数字）。技术上讲这个参数叫什么名字都行，但沿用 `n` 就好；
- 求平方就是"自己乘自己"，所以 `return n * n`。当然也可以用别的语法（比如 `n ** 2`），但当时我们最终定下来的是这种写法；
- 最后调用 `main` 来启动整个程序。

先手动测一下：

```
$ python calculator.py
What's x? 2
x squared is 4
```

`2` 的平方是 `4`，对。再跑一次：

```
$ python calculator.py
What's x? 3
x squared is 9
```

`3` 的平方是 `9`，也对。这时候你可能自我感觉良好，然后就去提交作业、或者把代码发到网上给别人用了。

## 2. 手动测试的问题 + 为什么要加 `if __name__ == "__main__"` [00:03]

但实际上，我们并没有**系统地（methodically）**测试这段代码。它未必真的完全正确——我们压根没考虑过各种**边界情况（corner cases）**。我们只试了 2 和 3 这种"显而易见的数字"，那 0 呢？负数呢？还有无穷多个别的数字呢？

我们当然不可能把无限多个输入都试一遍——那样程序永远不会停机。但我们应该去测一些**有代表性的输入**。

不过在动手写测试之前，先改掉一个习惯：**不要总是无脑调用 `main`**。现在开始，请一律采用这个写法：

```python
if __name__ == "__main__":
    main()
```

意思是：**只有当这个条件成立时，才去执行 `main`**。

为什么要"抢先"做这件事？David 特别强调了动机：因为我马上要把 `square` 函数**导入（import）**到另一个文件里去，把它当成自己的一个库来用。我必须保证在导入的时候，`main` 不会自动跑起来。

> 这是本讲的第一个关键铺垫：**如果 `calculator.py` 末尾直接写 `main()`，那么别的测试文件一 `import` 它，它就会开始问用户"What's x?"，然后卡在那里。** 加了条件判断，导入就安全了。

## 3. 第一个测试程序：test_calculator.py（if + print 版）[00:05]

现在我们有了一个"真正的" `calculator.py`，也准备好了条件调用 `main`，可以安全地从别的文件里 import 它的东西了。

按**约定（convention）**，新建一个测试文件，文件名以 `test_` 开头，后面跟被测程序的名字：

```
$ code test_calculator.py
```

这个文件是**一个全新的、独立的程序**，它存在的唯一目的就是测试 `calculator.py`——更准确地说，是测试里面那个 `square` 函数的功能。

先解决第一个问题：怎么在这个文件里访问 `square`？

回忆一下：我们可以把另一个 `.py` 文件当成自己的库（也就是所谓的**模块 module**）来 import。所以：

```python
from calculator import square


def main():
    test_square()


def test_square():
    if square(2) != 4:
        print("2 squared was not 4")
    if square(3) != 9:
        print("3 squared was not 9")


if __name__ == "__main__":
    main()
```

逐条拆解：

- `from calculator import square`：从 `calculator` 这个文件里，把 `square` 函数导入进来。
  - 也可以写 `import square` 或者 `import calculator`，但那样你每次用 `square` 都得写成 `calculator.square(...)`，多写一个前缀。**只 import 这一个函数，代码更干净**——这是 David 明确说的偏好。
- 定义一个函数叫 `test_square`，这也是约定：想测 `square`，测试函数就叫 `test_square`（也有人写 `square_test`，本讲统一用 `test_` 前缀）。
- 测试逻辑是"反向"的：我**不**检查它等于什么，而是检查"它**不等于** 4 吗？"——如果不是 4，那就说明程序里有 bug，就 `print` 一句提示。
- 打印什么内容其实随意，目的是让我或别人知道："2 的平方不是 4"。
- 光定义 `test_square` 还不够，得有人调用它。所以这个测试文件里**也**定义一个 `main`，`main` 的唯一职责就是调用 `test_square`。
- 文件末尾同样加上 `if __name__ == "__main__": main()`，理由还是那个：万一以后别人 import 这个测试文件，也不会自动跑起来。

**这里 David 点明了一件事**：这其实是**样板代码（boilerplate）**——定义 `main`、调用 `main`、末尾加条件判断，这些我们以前都见过，现在只是把同样的习惯搬到测试文件里而已。

跑一下：

```
$ python test_calculator.py
```

**没有任何输出。** 但没有输出其实是好事——因为看 `test_square` 的逻辑：一切正常时它什么都不打印。

## 4. 故意造个 bug：为什么只有一条测试报错？[00:08]

为了验证"没有输出 = 测试通过"这个假设，我们**故意把 `calculator.py` 弄坏**。假设我们第一次写代码时压根没想清楚，忘了"平方"是什么，误以为一个数的平方就是 `n + n`：

```python
def main():
    x = int(input("What's x? "))
    print("x squared is", square(x))


def square(n):
    return n + n          # 故意写错：本来应该是 n * n


if __name__ == "__main__":
    main()
```

（这是一个很合理的"算术错误"，不是粗心，是理解错了。）

现在 `test_calculator.py` **一行都不改**，重新跑：

```
$ python test_calculator.py
3 squared was not 9
```

报错了。但这里有个**非常有意思的疑点**：我把 `square` 函数彻底写坏了（数学上完全错了），可是**只有一条**测试报错？看起来测 `2` 的那两行通过了（没输出），测 `3` 的那两行失败了。

David 把问题抛给同学："为什么我只看到一个错误，而不是两个？明明 `square` 函数已经坏了。"

学生回答：**"因为 2 + 2 等于 4。"**

对，就是这么简单。我们**运气好**——`2 + 2` 和 `2 * 2` 结果恰好一样。这就是一个典型的 corner case，也是为什么**不应该只测一个值，而要测好几个值、尽量覆盖各种情况（cover your bases）**。

> 本讲第一记重锤：**如果你的测试只测 2，那么 `n + n` 这种 bug 你就永远发现不了。**

## 5. `assert` 关键字：把测试从四行压到两行 [00:11]

先别急着高兴——从这个例子往外推：如果我要跑的不是 2 个测试，而是 3 个、4 个、10 个、20 个呢？测试代码会膨胀得比被测代码本身还复杂。

看现实：**`calculator.py` 里被测函数只有 2 行，而 `test_calculator.py` 里的测试代码有 5 行。** 为了测代码，我写的代码比原始代码还多。

David 的原话很关键：**"测试时写的代码行数越少，你我越有可能真的去写测试"** —— 因为活儿更少，出错的机会也更少。

那还有什么别的办法？Python 里有一个我们还没用过的**关键字（keyword）**：

```
assert
```

`assert` 就是英文里的"断言"——大胆声明某件事是真的。

- 如果它**确实是**真的：什么都不会发生，屏幕上不会出现任何错误；
- 如果它为**假**（也就是你断言的那个**布尔表达式 Boolean expression** 求值为 `False`）：屏幕上就会出现某种错误。

把测试代码改成这样：

```python
from calculator import square


def main():
    test_square()


def test_square():
    assert square(2) == 4
    assert square(3) == 9


if __name__ == "__main__":
    main()
```

注意逻辑**反转**了：以前是"检查它是否**不等于** 4"，现在是**大声断言"它就应该等于 4"**。而且不再有缩进的 `print`，就只是断言这两件事为真。代码从 4 行降到 2 行。

此时 `calculator.py` 仍然是坏的（还在用 `+`），再跑一次：

```
$ python test_calculator.py
```

屏幕上冒出**一大堆错误**。往上翻看 traceback（回溯信息），会看到真正失败的是这一行：

```python
assert square(3) == 9
```

**这里有个必须记住的缺点**：`assert` 关键字对用户**不太友好**。它只告诉你是哪个文件、哪一行，并把失败的那行断言代码显示出来；至于"为什么 3 的平方不等于 9"，得靠你自己去推断。

不过优点是实打实的：**代码量只有一半**，就两行。

## 6. `AssertionError` 与 try/except：能用，但代码量反弹 [00:12]

看输出末尾那行小字：这是一个 **`AssertionError`**（断言错误）。

我们以前见过各种错误，以前遇到错误的解决办法是什么？学生回答：**`try` 和 `except`。**

对——在 Python 里可以用 `try` / `except` 先乐观地"尝试"做某事，如果出错了就"转而"做别的事。这条思路是对的，我们至少能把这个错误**接住**。

但 David 提前坦白：这其实也是**倒退一步**，因为代码会变得更多。

```python
from calculator import square


def main():
    test_square()


def test_square():
    try:
        assert square(2) == 4
    except AssertionError:
        print("2 squared is not 4")
    try:
        assert square(3) == 9
    except AssertionError:
        print("3 squared is not 9")
    try:
        assert square(-2) == 4
    except AssertionError:
        print("-2 squared is not 4")
    try:
        assert square(-3) == 9
    except AssertionError:
        print("-3 squared is not 9")
    try:
        assert square(0) == 0
    except AssertionError:
        print("0 squared is not 0")


if __name__ == "__main__":
    main()
```

（上面是"加满测试值"之后的完整版，下面第 7 节讲为什么加这些值。）

这样写：不再是盲目地 `assert`，而是"尝试断言，除非（except）抛出 `AssertionError`，那就打印一句更友好的解释"。

重新跑：

```
$ python test_calculator.py
3 squared was not 9
-2 squared was not 4
-3 squared was not 9
```

仍然是失败（因为有输出），但至少**输出又变回人类看得懂的话**了。这算是一种进步。可代价是代码更多了，而且如果你还要继续加测试用例，代码只会越来越长。

> 小结这一步的取舍：
> - `if + print`：友好，但繁琐
> - `assert`：简洁，但不友好
> - `assert + try/except`：既严谨又友好，但**代码最多**

## 7. 测试哪些值？负数、0 与"代表性取值"的思路 [00:15]

继续想：现在只测了 2 和 3，**负数是不是也该测？** 于是复制粘贴，加上：

- `square(-2)` 应该等于 4（数学上确实如此）
- `square(-3)` 应该等于 9

David 一边写一边"自言自语"地思考：我已经试了 2、3、-2、-3，**我没法试完无限多个数**。但至少在这些值之间，还有个不太一样的东西值得试——**0**。

为什么是 0？David 坦白说这就是**直觉、本能（instincts）**，没有什么科学公式：

- 正数大概率表现得都差不多；
- 负数大概率表现得都差不多；
- **0 可能有点反常（anomalous）**。

所以真正的思路是：**基于你自己的经验，针对你正在测的那个函数，去想"哪些是潜在的边界情况"**。我测的是一个数学函数，那我就要测**有代表性的取值（representative values）**——每一类挑一两个。

于是再加一条：

```python
    try:
        assert square(0) == 0
    except AssertionError:
        print("0 squared was not 0")
```

再跑一遍（此时 `square` 还是 `n + n`），现在**看到多个错误**，而这本身就是一条线索：**有些断言失败了，有些没有**。

逐个分析（这是本讲非常精彩的一段推理）：

- `square(2)`：**通过**。因为 2 的平方恰好等于 2+2，这个 bug 没被这个测试抓到。幸好我们测了 3。
- `square(3)`：**失败**。
- `square(-2)`：**失败**。注意，正 2 我们"运气好"蒙混过关，但负 2 就没这么幸运了。
- `square(-3)`：**失败**。
- `square(0)`：**通过**。因为 0 的平方是 0，而 0+0 也是 0——这里又"幸运/不幸"地躲过去了。

结论：**幸好有多个测试，才以某种方式把这个错误抓了出来。**

但紧接着是 David 的灵魂拷问：`try`、`except`、一个个 `assert`、一个 `main`、一个 `if` 条件……**现在为了测一个两行的函数，我要写 31 行代码。谁会愿意这么写测试？没人会。**

> 本讲的核心矛盾就在这里：**测试很重要，但手写测试太贵**。接下来就是解决办法。

## 8. pytest 登场：让工具替你写 try/except/main/print [00:17]

这个问题的解法是：既然你、我、现实世界里的每个人都想大量测试自己的代码，那就**造工具**来简化这件事。这个工具就叫 **`pytest`**。

关于 pytest 的几个要点：

- 它是一个**第三方程序 / 第三方库（third-party library）**，需要下载安装；
- 它能**自动化（automate）**跑测试——前提是你得**自己写出测试**；
- 它好用的关键在于：**它采纳了一套约定**，于是 `try`、`except`、`print`、标准化的运行流程这些脏活它全替你干了，你只要写测试的"本质"；
- Python 自带也有单元测试框架（标准库里有），但本讲选 pytest，因为它**比 Python 自带的那些更简单**。

安装方式（`pip` 我们以前装别的库时也用过）：

```
$ pip install pytest
```

## 9. 用 pytest 重写测试：砍掉 main、条件、try、except、print [00:20]

回到 VS Code，把原来那 31 行的测试**大幅精简**——那些不断累积的测试全删掉，看看用 pytest 能把测试"提纯"到什么程度。

```python
from calculator import square


def test_square():
    assert square(2) == 4
    assert square(3) == 9
```

## 15. 改进：把测试拆成多个函数（test_positive / test_negative / test_zero）[00:30]

## 20. 测试"应该抛异常"的情况：pytest.raises(TypeError) [00:37]

顺着上面的讨论，David 提出：那我们来考虑一下，**如果 `square` 拿到的根本不是数字，应该发生什么？**

假设在 `calculator.py` 里，我（或者用我这个函数的别人）**忘了**把 `input` 的返回值从 `str`（字符串）转成 `int`，把第 2 行改成：

```python
def main():
    x = input("What's x? ")     # 故意漏掉 int()，x 现在是字符串
    print("x squared is", square(x))


def square(n):
    return n * n


if __name__ == "__main__":
    main()
```

这时候如果用户输入 `cat`，肯定要出事：

```

```

会抛出 `TypeError`（类型错误），提示信息类似：

```
TypeError: can't multiply sequence by non-int of type 'str'
```

意思是：`cat` 乘 `cat` 是做不到的，因为 `square` 期待 `n` 是个数字。

**注意 David 的思路**：这**不一定**说明 `square` 本身有 bug。但**如果我预期会抛出 `TypeError`，那我就应该为"它会抛"这件事也写个测试**，用来确认行为确实符合预期。

回到 `test_calculator.py`，加第四个测试：

```python
import pytest

from calculator import square


def test_positive():
    assert square(2) == 4
    assert square(3) == 9


def test_negative():
    assert square(-2) == 4
    assert square(-3) == 9


def test_zero():
    assert square(0) == 0


def test_str():
    with pytest.raises(TypeError):
        square("cat")
```

要点：

- 想表达"传入 `cat` 应该引发 `TypeError`"，**不能**用 `assert` 关键字，得用别的东西；
- 所以要到文件顶部**额外导入 pytest 库本身**：`import pytest`；
- pytest 库里有一个函数叫 **`raises`**，专门用来表达"我预期会抛出一个异常"；
- 写法是 `with pytest.raises(TypeError):`，括号里传入你期望的异常类型（这里是 `TypeError`），缩进的代码块里放"会触发该异常的操作"——这里就是 `square("cat")`。

这次连提示都没有了（因为我把 `input` 删了），但行为符合预期：**打印出了 "hello, world"**。

所以 David 明确定调：**当前这份 `hello.py` 代码是正确的，出问题的是我的测试。** 那么——`hello` 函数和 `square` 函数之间，到底有什么微妙差别，导致这个测试不能按我期望的方式工作？

**学生回答二（正确）**：**因为它没有返回值。**

## 23. 副作用 vs 返回值：为什么 `print` 不可测 [00:42]

对，正是如此。回忆我们很早以前对函数的讨论：

- 函数**可以返回一个值（return a value）**，比如 `square` 把平方结果"交还"给你；
- 函数也**可以有副作用（side effects）**——也就是发生在屏幕上的"视觉产物"，比如**往屏幕上打印了点东西**。按定义，`print` 就是这么工作的。

注意 `hello` 虽然短，但它底层是用 `print` 实现的，而这个 `print` **没有返回值**——它只有"往屏幕上打印"这个副作用。

所以在测试里写 `hello("David") == "hello, David"` 是**不正确的**，因为 `hello` 什么都没返回。它只是打印了东西（副作用）。从字面上看：**它里面根本没有 `return` 关键字**，而 `square` 里有。

---

## 24. 改造 hello.py：用 f-string 返回值，把 print 交给调用方 [00:42]

这就给了我们一个机会去改变"实现函数的方式"。

**经验法则（这是本讲的设计原则）**：随着程序越来越复杂、越来越庞大，**最好的做法是尽量避免副作用**——尤其在你希望代码**可被测试**的时候。

于是 David 提议把 `hello` 改成下面这样：不再 `print`，而是**返回一个 f-string（格式字符串 f-string / format string）**：

```python
def main():
    name = input("What's your name? ")
    print(hello(name))


def hello(to="world"):
    return f"hello, {to}"


if __name__ == "__main__":
    main()
```

变化细节：

- `hello` 函数体从 `print("hello,", to)` 变成 `return f"hello, {to}"`。这个 f-string 会根据传入的名字生成 `"hello, world"` 或 `"hello, David"` 或任何名字——**但我是把它返回，而不是打印出来**；
- 那么 `main` 里要改什么？可以先写成两步：

  ```python
  output = hello(name)
  print(output)
  ```

  但那个变量其实没必要，可以简化成一步——**调用 `hello` 的同时立刻 `print` 它的返回值**：

  ```python
  print(hello(name))
  ```

**为什么这样一改就"更可测"了？** 因为我们用的 `assert` 语句，本质上设计来测的是**传给函数的参数（arguments）和函数返回的值（return values）**，而不是副作用。

只要你在做 `==` 比较，你就是在找**一个从函数里交回来的返回值**。所以：**把程序从"打印结果"改成"构造并返回那个字符串/句子/短语"，把真正的打印工作留给调用方（caller，也就是使用这个函数的那个函数）。**

## 25. 跑通 test_hello.py，并拆成两个测试函数 [00:45]

现在 `hello.py` 里的 `hello` 确实有返回值了，测试里就可以这么写：

```python
from hello import hello


def test_hello():
    assert hello("David") == "hello, David"
    assert hello() == "hello, world"
```

跑一下：

```
$ pytest test_hello.py

test_hello.py .                                                         [100%]

```

"voilà，1 passed（通过 1 个）"。两条断言都通过了：

- `hello("David")` 的返回值确实等于 `"hello, David"`；
- `hello()` 不传参数时，返回值等于 `"hello, world"`（因为 `to` 的默认值是 `"world"`）。

不过，**把多个断言塞在同一个函数里不是最佳实践**——一旦有 bug，看不出是哪条挂了。所以拆开，让"什么通过、什么失败"更清楚：

```python
from hello import hello


def test_default():
    assert hello() == "hello, world"


def test_argument():
    assert hello("David") == "hello, David"
```

- `test_default`：测**默认情况**（不传参数）；
- `test_argument`：测**传参数**的情况。

两个测试测的是本质上不同的两件事。再跑：

```
$ pytest test_hello.py

collected 2 items

test_hello.py ..                                                        [100%]

============================== 2 passed in 0.02s ==============================
```

现在通过 2 个测试，跟之前效果一样好。**但如果代码里有 bug，两条测试（而不是一条）能给你更多提示，指出到底哪儿错了。**

**回答**：如果你有一个递归函数（虽然这门课不讨论），**当然也能测**——就按现在完全一样的方式去调用它就行。**递归不影响这个测试流程。**

## 27. 学生提问八：测试里能用循环吗？[00:48]

**学生问**：测试参数的时候，能不能用循环来遍历多个值？

**回答：完全可以。** 比如可以这样：

```python
from hello import hello


def test_argument():
    for name in ["Hermione", "Harry", "Ron"]:
        assert hello(name) == f"hello, {name}"
```

解释一下：用 `for` 循环遍历一个列表（哈利波特三人组），在循环体里断言 `hello(name)` 等于对应的 f-string。

跑 `pytest test_hello.py` 时，**在 pytest 眼里这仍然只是"一个测试"**（一个测试函数里的测试）。但如果你觉得这几个字符串有什么特别之处、值得全测一遍，用循环自动化完全可以。

**不过 David 立刻加了限制（这一条要记住）**：

> **你的每一个测试，理想情况下都应该相当简单、相当短小。**

为什么？因为你不希望为了测试而写出一大堆复杂的代码——**那你的测试本身可能也会有 bug**。我们绝不想陷入"为测试写测试、再为测试的测试写测试"的无限循环，那样永远没完。

**保持测试简洁才是目标**，这样任何一个正常的人（包括你自己）瞄一眼就能拍板说："对，这是对的。"——**我们不需要给测试写测试。**

## 28. 把测试组织进文件夹：mkdir test + __init__.py + pytest test [00:50]

最后一个功能：假设你不只有一个测试，而有很多个测试，想把它们**组织进多个文件、甚至一个文件夹**。pytest 这类框架支持这种做法。

第一步，在命令行里创建一个叫 `test` 的文件夹（`mkdir` = make directory）：

```
$ mkdir test
```

第二步，在这个文件夹里创建测试文件（`test/` 前缀告诉终端：在 `test` 这个文件夹里创建）：

```
$ code test/test_hello.py
```

内容和之前几乎一样：

```python
from hello import hello


def test_default():
    assert hello() == "hello, world"


def test_argument():
    assert hello("David") == "hello, David"
```

也就是说：**把之前的测试原样重建，只不过这次放在了 `test` 文件夹里的一个文件中。**

第三步（**关键，最容易漏的一步**）：光有这个文件（或一整批文件）**还不够**，pytest 不允许你直接对整个文件夹跑测试。你必须在 `test` 目录里再创建一个特殊文件：

```
$ code test/__init__.py
```

注意两点：路径里的 `test/`，以及 `init` 两边**各两个下划线**（`__init__.py`）。

这个文件的作用：**即使它完全是空的**，它的存在也会告诉 Python——把那个文件夹当作不只是一个模块，而是一个 **package（包）**。

- **package（包）** = 组织在一个文件夹里的一个 Python 模块或多个模块；
- `__init__.py` 就是给 Python 的一个**视觉标记（visual indicator）**：这个文件夹应当被当作一个包来对待。
- 如果以后这个文件夹里有更多代码，你还可以在 `__init__.py` 里做更多事情；**但现在它只是个标记**，表明"这是一个包，而不是单独的一个模块或文件"。

最后，不必指定某个具体文件，直接对**整个文件夹**跑 pytest（`test` 是文件夹名）：

```
$ pytest test
============================= test session starts ==============================
platform linux -- Python 3.11.x, pytest-7.4.x, pluggy-1.3.0
rootdir: /workspaces/12345678
collected 2 items

test/test_hello.py ..                                                   [100%]

============================== 2 passed in 0.03s ==============================
```

**pytest 会自动搜索那个文件夹，找出所有可能的测试。** 当前只有这一个文件里的两个测试，但仍然全部通过、100% 成功。于是我们就有了一套测试自己代码的机制。

无论你写的是返回整数的函数，还是别的类型的函数；无论你的函数是带有副作用（**可以改写成返回值的形式**），还是本来就在返回值——你现在都拥有了一套机制：

- 不用再等着别人（比如我们）来测你的代码；

## 本讲代码速查

```python
# ---------- 被测试的程序：calculator.py ----------
def main():
    x = int(input("What's x? "))
    print("x squared is", square(x))


def square(n):
    return n * n


if __name__ == "__main__":        # 只在直接运行时才调用 main，被 import 时不会自动执行
    main()


# ---------- 测试文件命名与导入 ----------
# 文件名约定：test_calculator.py  /  test_hello.py
from calculator import square     # 从 calculator.py 里导入 square 函数
from hello import hello           # 从 hello.py（模块）里导入 hello（函数）


# ---------- 第一版测试：if + print ----------
def test_square():
    if square(2) != 4:
        print("2 squared was not 4")
    if square(3) != 9:
        print("3 squared was not 9")


# ---------- assert 关键字 ----------
assert square(2) == 4             # 断言布尔表达式为真；为假则抛出 AssertionError


# ---------- try / except 捕获断言错误 ----------
try:
    assert square(2) == 4
except AssertionError:
    print("2 squared is not 4")


# ---------- pytest 版本（没有 main、没有条件、没有 try/except/print）----------
def test_positive():
    assert square(2) == 4
    assert square(3) == 9


def test_negative():
    assert square(-2) == 4
    assert square(-3) == 9


def test_zero():
    assert square(0) == 0


# ---------- 测试"应当抛出的异常" ----------
import pytest

def test_str():
    with pytest.raises(TypeError):
        square("cat")


# ---------- 可测试的函数：返回值，而不是打印 ----------
def hello(to="world"):            # to 有默认值 "world"
    return f"hello, {to}"         # f-string 格式化字符串


def main():
    name = input("What's your name? ")
    print(hello(name))            # 把打印交给调用方


# ---------- 用循环批量断言（测试要尽量简单）----------
def test_argument():
    for name in ["Hermione", "Harry", "Ron"]:
        assert hello(name) == f"hello, {name}"
```

```bash
# ---------- 本讲所有命令行操作 ----------
pip install pytest        # 安装第三方测试框架 pytest
code calculator.py        # 用 VS Code 打开/新建文件
python calculator.py      # 运行程序（手动测试）
python test_calculator.py # 用 python 跑测试（早期版本）
pytest test_calculator.py # 用 pytest 跑测试文件
pytest test_hello.py      # 跑另一个测试文件
mkdir test                # 创建 test 文件夹
code test/test_hello.py   # 在 test 文件夹里建测试文件
code test/__init__.py     # 建空的 __init__.py，让该文件夹成为 package
pytest test               # 对整个文件夹跑测试
```

**pytest 输出符号速记**

- `.`（绿色的点）= 该测试通过
- `F` = 该测试失败（Fail）
- `E` = 输出中具体出错的那一行
- 底部汇总行：`3 passed` / `2 failed, 1 passed`

## 本讲易错点

1. **测试函数只有 2 是不够的。** 只测 `square(2)` 时，`n + n` 这种 bug 永远抓不到，因为 `2 + 2 == 2 * 2`。同理 `square(0)` 也抓不到（`0 + 0 == 0 * 0`）。必须测多个、多类别的值：正数、负数、0。
2. **`calculator.py` 末尾不加 `if __name__ == "__main__":` 就完蛋。** 一旦测试文件 `import` 它，`main()` 会被自动执行，程序会开始等用户输入，测试就卡死或行为异常。
3. **只定义了 `test_square` 函数，它不会自己运行。** 早期版本必须自己写 `main()` 调用它、并在文件末尾条件调用 `main`。换成 pytest 之后这些才不需要。
4. **`assert` 输出不友好。** 它只告诉你哪一行断言失败（配合 traceback），不会解释为什么。这是后来引入 pytest 的动机之一。
5. **一个测试函数里第一条断言失败，后面的断言就不会执行了。** 所以要把测试拆成 `test_positive` / `test_negative` / `test_zero` 等多个函数——pytest 会全部尝试运行，给你更多线索。
6. **"全部通过"不等于"代码正确"。** 它只表示通过你当前写的这些测试。要不要测更大的数、更小的数、字符串，责任在你。另外**浮点数（float）不适合做 `==` 相等断言**——Python 里的浮点数无法 100% 精确表示，比较时可能出现舍入误差，所以本讲刻意只用整数测 `square`。
7. **`print` 的函数没法用 `==` 比较。** `print` 是副作用，没有返回值；`hello("David") == "hello, David"` 对 `print` 版 `hello` 永远失败。正确做法是把函数改成 `return f"hello, {to}"`，由调用方去 `print`。
8. **测试异常不能用 `assert`。** 要用 `import pytest` + `with pytest.raises(TypeError):` 包住会触发异常的调用。
9. **放进文件夹的测试跑不起来，多半是少了 `test/__init__.py`。** 这个空文件是"这是一个 package"的标记；注意 `init` 前后各两个下划线。
10. **测试不是越复杂越好。** 可以用循环、列表、字典批量生成断言，但每个测试应尽量短小简单——否则你还得给测试写测试，没完没了。
