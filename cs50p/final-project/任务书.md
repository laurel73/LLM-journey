## 一、题目（一句话）

**把你电脑里的一堆文档建成索引，用自然语言问它问题，它给出答案并标出「这句话出自哪个文件的哪一段」，还能告诉你这次问花了多少钱。**

```
$ python project.py index ./notes
索引 47 个文件 → 312 个片段（新增 18，跳过 294，重写 0）
嵌入调用 18 次，花费 ¥0.031

$ python project.py ask "我上次记的 pytest  fixture 用法是什么？"
答案：……（基于 3 个片段生成）

来源：
  1. notes/CS50P-Python知识点汇总.md  第 12 节（相关度 0.81）
  2. notes/CS50P-分集笔记-含习题.md    P7 单元测试（相关度 0.74）
本次花费 ¥0.004｜累计 ¥0.035
```

## 二、为什么是这道题

**它直接通向你想学的方向，但不是「把 API 包一层」。** 大家做 LLM 作业最常见的样子是一个 `while True: 问 → 打印` 的聊天框，做完你其实什么都没学到。这道题逼你亲手实现聊天框背后的东西：**文本怎么切、怎么找、怎么证明找对了、怎么不重复花钱**。

**四个真难点，全在 CS50P 范围内：**

1. **文本切分（chunking）**。整篇塞进去太长，按字符硬切会把句子劈断。要按段落/标题切，控制长度并留重叠。切得好不好，直接决定检索准不准——这是你能自己调、自己看效果的部分。
2. **相似度检索要自己算**。调 API 拿到向量（一串数字）之后，用**余弦相似度**找出最相关的几段，这个函数三十行，纯 Python 写，不许调库。这是整个项目里最「计算机」的一段。
3. **增量索引与缓存**。第二次运行时只对新增/改动的文档重新嵌入（用文件哈希判断），embedding 结果存本地。**不做这个，你每次跑一遍都要重新花钱**，而且跑一次几十个文件你自己都不敢试。
4. **测试里不能真调 API**。要测 `answer()` 但又不能每次跑测试都花钱联网——用假数据（monkeypatch / 自己写个假客户端）把网络那层替掉。这是真实工程里的基本功，也是你作业能稳定提交的前提。

**它做完你自己天天能用。** 你手上已经有 CS50P 笔记、学习日志、项目文档，直接拿来当语料。不是做完就扔的作业。

## 四、建议的函数结构

```python
def main():                                  # CLI：index / ask / stats / eval
    ...

def chunk_text(text: str, size: int = 500, overlap: int = 80) -> list[str]:
    """按段落切分，控制长度，相邻片段留重叠"""

def build_index(path: str) -> dict:
    """遍历目录，按哈希判断新增/修改，只对变化的调 embedding，落盘缓存"""

def search(query: str, index: dict, k: int = 3) -> list[dict]:
    """把 query 向量化，与所有片段算余弦相似度，返回 top-k（含来源与分数）"""

def answer(query: str, index: dict) -> str:
    """组装提示词调用 LLM，返回带来源标注的答案"""
```

`test_project.py` 对应 `test_chunk_text` / `test_build_index` / `test_search` / `test_answer`，重点是后两个**用假向量和假 LLM 响应**测，不联网。

辅助模块（`embeddings.py` / `llm.py` / `store.py`）可另开文件，官方不限制。

## 五、分阶段推进

**第一周 · 离线骨架**：`chunk_text` + 假向量跑通 `search` 的余弦相似度（先不接 API）。用 10 个手工构造的片段手工验证「相关的排在前面」。这一步做完，项目最难的部分就过去了。

**第二周 · 接 API**：选一个 OpenAI 兼容的服务（DeepSeek / 智谱 / 硅基流动 / 你已有的 DashScope 都行），接 embedding 与 chat 两个接口，跑通 `index` + `ask`。**先只索引 5 个文件**，确认花钱速度再放大。

**第三周 · 工程化**：增量索引（哈希比对）、本地缓存、失败重试与限速、成本统计与 `--dry-run`（打印将要花多少钱但不真的调）。

**第四周 · 收尾**：`eval` 子命令（见下）、README、pytest 全绿、录视频。

## 六、加分项：一个 `eval` 子命令（这一项最能拉开差距）

自己造 **20 个问题**，每个问题手工标注「正确答案应该来自哪个片段」，存成 `data/eval_set.json`。然后写 `eval` 命令：批量跑检索，统计**「正确来源是否出现在 top-3 里」**——这就是检索召回率。

有了它，你调切分参数（size/overlap）时就有了一把尺子：改之前多少、改之后多少，写在 README 里。**作业里几乎没人做这个，而它是「你怎么知道它是对的」的唯一答案。**

## 七、明确不要做

- 不要做网页界面（Streamlit/Gradio）。终端就够，省下的时间做检索质量。
- 不要引入向量数据库（Chroma/Faiss）。几十到几百个片段，纯 Python 算余弦相似度完全够，引入它们反而把你最该练的东西跳过了。
- 不要做多轮对话记忆。单轮问答做扎实就够。
- 不要一上来索引几千个文件。先用 20 个文件跑通全流程。

## 八、成本与选型提示

- Embedding 几千个片段通常就几毛到几块钱；单次问答几分钱。**先跑小样本确认单价再放量**，这是习惯问题。
- 所有 key 走环境变量（`os.environ["API_KEY"]`），`.env` 加进 `.gitignore`，README 里写明需要设置哪些环境变量。
- 每次真实调用落一条日志（时间、token 数、花费），既是成本账本，也是你调试时的证据。
